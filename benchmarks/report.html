What was measured

Production React in Chromium with controlled commit checkpoints and consistent flushSync scheduling across libraries. This measures controlled commit cost, not natural event latency or concurrent scheduling. Each case receives 2 warmups and 5 repeated samples. Case order is randomized with seed 20261020.

Controlled commit benchmark: one synchronous logical transaction, one microtask checkpoint, then the same React flushSync checkpoint for every library; timing includes notification delivery and DOM commits, excludes correctness checks. No frame or paint wait.

Adapters use compiled useService, MobX observer, Zustand selectors with one immutable publication per transaction, and Valtio snapshots scoped to stable rows/nested objects. Collection replacement and derivation use root snapshots so replaced data is observed.

Bars show the median. P95 is the nearest-rank percentile. For update time, P95 is computed over per-sample average ms/op; it is not individual-operation latency P95. The range preserves sample variation; update time and render calls are normalized by operations. Mount and unmount measure the complete consumer tree.

Setup includes adapter/store construction and initial data allocation. Startup adds setup and mount within each sample. Compare startup rather than mount alone: libraries may initialize reactive data eagerly during setup or lazily during mount.

Read counts with context

Lower is better for time and render-call counts. Fewer renders alone do not guarantee a faster update; check elapsed time too. Render calls are component function executions during updates, not paints. Array dependency strategies differ: MobX can legitimately rerender more array consumers. No overall library ranking is computed.

These timings exclude browser paint, network latency, and virtualization libraries.

  • Single machine, single browser process, sequential warmed runs; timings are not cross-device performance guarantees.
  • Headless browser commit latency excludes paint, layout measurement, network, real API libraries and user-event dispatch.
  • Large arrays use a bounded visible window; this is not a virtualization-library benchmark.
  • Zustand uses one structurally shared immutable publication per transaction; proxy libraries mutate in place. Representation costs are included.
  • Results are scenario-specific. Do not combine different workloads into an overall winner.
  • Fresh stores and roots for every sample; setup and teardown are measured separately. No forced garbage collection; allocation and GC can affect outliers.

Methodology references: React flushSync, MobX reactivity, Zustand immutable updates, Valtio useSnapshot.
